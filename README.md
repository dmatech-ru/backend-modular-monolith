# Backend Modular Monolith on Go

Высокопроизводительный бэкенд-сервис на Go, спроектированный по архитектуре **модульного монолита (Modular Monolith)**. Проект ориентирован на максимальную изолированность бизнес-доменов (low coupling) при сохранении простоты деплоя единого бинарного приложения.

Взаимодействие между модулями и динамическим шлюзом (Gateway) построено на базе **Protobuf-дескрипторов** и реактивного **Service Discovery поверх NATS JetStream KV**.

---

## 🏗 Ключевые архитектурные решения

### 1. Децентрализованный Service Discovery (пакет `natsrpc`)
Вместо использования тяжелых сторонних решений (Consul, etcd), в систему встроен легковесный реактивный реестр на базе **NATS JetStream Key-Value Store**:
* **Разделение данных (Split Routing):** Тяжелые бинарные дескрипторы маршрутов (`routes`) отделены от легковесных хартбитов присутствия (`nodes`). Это минимизирует нагрузку на сеть и диск.
* **Идемпотентность и Оптимизация:** При старте новых реплик пакет проверяет наличие схемы (`kv.Get`). Тяжелая запись дескрипторов происходит строго один раз.
* **Паттерн «Последний тушит свет» (Reference Counting):** При Graceful Shutdown ноды вычищают свой пульс. Последняя уходящая нода конкретной версии автоматически удаляет общий ключ маршрута.
* **Строгое Версионирование:** Пути ключей поддерживают формат `1_0_0`, что обеспечивает полную изоляцию поколений кода при мягком деплое (Rolling Updates).

### 2. Динамический Gateway
Модуль `gateway` работает как «умный» реверс-прокси:
* Он реактивно слушает изменения схем через встроенный `natsrpc.WatchRoutes`.
* Инфраструктурный слой автоматически дедуплицирует хартбиты в памяти с помощью криптографических хэшей (**SHA-256**), вызывая парсинг дескрипторов в гейтвее строго при обновлении кода.

## 📂 Структура проекта

```text
├── cmd/
│   ├── bootstrap/       # Фиксация пустых импортов для компиляции сгенерированного кода
│   └── builder/         # Основная точка входа, сборка и запуск приложения
├── configs/             # Конфигурационные файлы модулей (YAML)
├── internal/
│   ├── modules/         # Бизнес-модули монолита
│   │   ├── gateway/     # Реактивный шлюз (динамический прокси-сервер)
│   │   └── identity/    # Модуль аутентификации и работы с пользователями
│   └── pkg/             # Общие инфраструктурные пакеты
│       ├── config/      # Дженерик-загрузчик конфигураций приложения
│       ├── logger/      # Кастомный изолированный ColorHandler для slog (Dev/Prod)
│       └── natsrpc/     # Инфраструктура NATS: NewConnection, RegisterDescriptors, WatchRoutes
├── Makefile             # Команды автоматизации сборки и генерации кода
└── go.mod               # Управление зависимостями проекта
```

## 🛠 Спецификация путей Service Discovery в NATS

Реестр использует бакет `service_discovery` и распределяет данные по иерархическим топикам:

| Тип данных | Шаблон ключа NATS | Описание | TTL |
| :--- | :--- | :--- | :--- |
| **Маршруты** | `discovery.{env}.routes.{service_name}.{version}` | Бинарный дескриптор Buf (`.bf` / `.pb`) | Нет |
| **Ноды** | `discovery.{env}.nodes.{service_name}.{version}.{hostname}` | Флаг присутствия конкретного инстанса | 10 секунд |

*Версии в путях автоматически нормализуются из формата `1.0.0` в безопасный для NATS формат `1_0_0` [1].*

## 🔄 Жизненный цикл бизнес-модуля (Пример)

Для подключения любого модуля к экосистеме монолита достаточно одной декларативной строчки в его инициализации:

```go
func initialization(ctx context.Context) error {
    cfg, _ := config.Load[configuration](CONFIG_PATH)
    nc, _ := service.Get[nats.Conn]()
    log := logger.NewModuleLogger(cfg.Module.ServiceName, cfg.Module.LogLevel)

    // Считываем сгенерированный дескриптор и отдаем его в natsrpc
    var descriptorBytes []byte 
    
    // Пакет сам займется проверкой, фоновым тикером Keep-Alive и зачисткой при закрытии ctx
    err := natsrpc.RegisterDescriptors(ctx, nc, cfg.Env, cfg.Module.ServiceName, cfg.Module.Version, descriptorBytes)
    return err
}
```
